# 制約一覧

実装と運用で守らなければならない制約。**調査で実際にぶつかったものだけ**を書く。

---

## Gmail 側の制約

### 1. フィルタはワイルドカードを解釈しない

現行フィルタの `from: *.agoda-emails.com` や `from: *@jalan\.net` は**動いていない**。
Gmail の検索構文に glob も正規表現も無い。`*` と `\` はただの文字として扱われる。

**対処**: `from_domain` は部分一致で書く (`jalan.net`)。`*` は使わない。
取り込み時に `*` を含むパターンは要確認として印を付ける。

### 2. 1 アカウント 1,000 フィルタ / 1 フィルタ 1,500 文字

現行の `from:({ a b c ... })` で束ねる書き方は**フィルタ数の上限を避けるための策**。
束が育つと 1,500 文字上限にぶつかって静かに壊れる。

**対処**: スプレッドシートを真実の源にする。1 行 1 ルールで束ねない。

### 3. 検索条件はメッセージ単位で評価される

スレッドは「いずれかのメッセージが条件に一致したら」返る。
そのため **`from:me AND from:seek.com.au` は「両方を同時に満たす 1 通」を探してしまい何も返らない**。

「スレッドに自分の送信が含まれ、かつ相手が求人サイト」という条件は検索式で書けない。

**対処**: `Work/Applications` は検索式ではなく、スレッドを走査して提案する
(`src/applied.ts`)。自動付与はしない。

### 4. `label:親` は子ラベルを含まない

`label:"Promotions/Jobs"` で `Promotions/Jobs/Alerts` は引けない。

**対処**: 接頭辞でラベルを列挙して `OR` で繋ぐ (`src/starwatch.ts`)。

### 5. 共有プラットフォームのドメインは `from_domain` で括れない

同じドメインから別々のサービスのメールが来る。

| ドメイン | 中身 |
| --- | --- |
| `m.shopifyemail.com` | 任意の Shopify ストア。`store+63532597474@` で識別するしかない |
| `zendesk.com` | `insta360jp.zendesk.com` は `Support`、`kdlsupport.zendesk.com` は povo で `Utilities` |
| `dmm.com` | `v-mail@` は英会話、`dmm-affiliate@` はアフィリエイト、`noreply-dmmclinic@` は医療 |
| `amazon.co.jp` | `shipment-tracking@` は注文、`store-news@` は販促 |

**対処**: これらは `from_domain` ではなく `from` (完全アドレス) かサブドメインで指定する。

ただし**共有ドメインでも用途が 1 つに揃っていれば括ってよい**。
`shop.rakuten.co.jp` は楽天市場の出店ショップごとに ID が違う共有ドメインだが、
全部が注文連絡なので `from_domain` で `Orders/Rakuten` に一括できる。

**判断基準は「ドメインが共有かどうか」ではなく「用途が揃っているかどうか」。**

### 5b. 逆に、同じ会社が複数のドメインを使う

`from_domain` を細かくすると今度は取りこぼす。

| 運営元 | ドメイン数 |
| --- | ---: |
| 楽天 | 5 |
| DMM | 4 |
| SHEIN | 4 |
| Amazon | 3 |
| JCB / DiDi / Google | 各 2 |

実際に **JCB は 2 つのサブドメインのうち片方だけラベルが付いていた**。
`qa.jcb.co.jp` は `CreditCards` の 100%、`cj.jcb.co.jp` は未分類のままだった。

**対処**: `senders` シートに `運営元` の列を持ち、会社単位で追えるようにする。
ルール自体はドメイン単位のままでよいが、**漏れの点検は運営元単位で行う**。

### 5c. 同じサービスでも拠点・支店ごとにアドレスが違う

5b とは逆に、`from` の完全一致では取りこぼすケース。

| サービス | アドレス |
| --- | --- |
| トランスコスモスパートナーズ | `fukuoka@` / `tokyo@` `ml.tcpartners.co.jp` |
| Anytime Fitness | `sunnybankhills@` / `armidale@` `anytimefitness.com.au` |
| CareSuper | `events@` / `caresuper@` `mail.caresuper.com.au` |

**判断基準: ドメインが 1 社専用なら `from_domain`、共有なら `from`。**

### 5d. 同じドメインの中で `@` の前の名前が系統を表す

| ローカルパート | 系統 | 例 |
| --- | --- | --- |
| `orders@` `accounts@` `system@` `inquiry@` `statement@` `auto-confirm@` `shipment-tracking@` | 取引・通知 | Hungry Jack's / Audiostock / TAION / 三井住友 / Amazon |
| `news@` `member@` `staff@` `store-news@` `point-` `marketing@` `promo` | 販促 | T2 Tea / TAION / Audiostock / Amazon / ぐるなび |
| `support@` `customerservice@` `cs-` | 問い合わせ | Agoda / Insta360 / スタディサプリ |
| `security` `no-reply@security.` | セキュリティ | Agoda |

**Agoda は 1 社で 4 系統に割れる**（予約確認 / 問い合わせ / セキュリティ / 販促）。
現行フィルタの `from: *.agoda-emails.com` はこの 4 つを区別できないどころか、
ワイルドカードが効かないので何も拾えていなかった。

判定の補助に使えるが、**規則ではなく傾向**。ルールは実際の観測で確定させる。

**反例: `rewards@mx.starbucks.co.jp` は販促ではない。** モバイルオーダーした商品を
受け取るときに必要な取引メールで、`Finance/Bills` に入る。`rewards@` という名前だけで
`Promotions` へ寄せると、**受信トレイから外れて既読になり、受け取りの場で見つからなくなる**。
ローカルパートで系統を決める前に、そのメールを**何に使っているか**を確かめる。

### 6. ラベル改名は割り当てを保持するが、統合は再タグ付けが要る

1:1 の改名は `Gmail.Users.Labels.patch` で一瞬。メールの割り当てはそのまま残る。
複数を 1 つにまとめる場合は、対象スレッド全部に新ラベルを付け直す必要がある。

## Apps Script 側の制約

| 制約 | 値 | 対処 |
| --- | --- | --- |
| 1 回の実行時間 | 6 分 | `PropertiesService` にカーソルを保存して分割実行 |
| `GmailApp` 日次クォータ | 読み取り 20,000 操作 / 日 (無料) | 遡及バッチはクォータ残を監視して自走停止 |
| `GmailApp.search()` | 1 回 500 件が目安 | `start` / `max` でページング |
| 任意ヘッダの取得 | `GmailApp` は露出しない | 高度なサービス `Gmail.Users.Messages.get` を使う。1 通 1 コールなので調査系に限る |

## 調査上の制約

### 検索して出なかったことは、存在しないことではない

`from:` や語句を指定した検索で「見つからなかった」を根拠に
カテゴリ不要と判断して、**3 回中 2 回外した**。

| 判断 | 結果 |
| --- | --- |
| ドメイン・ホスティングは無い | 5 巡目で **Netlify** が見つかった |
| 不動産・賃貸は無い | 6 巡目で **Flatmates** が見つかった |
| 保険は無い | 未確認のまま |

指定した検索語に含めていなかったサービスは、当然ヒットしない。
**カテゴリの有無は検索語ではなく、未分類メールの全数走査で判断する。**

### 1 時期だけ見ると必ず取りこぼす

| 時期 | 中心 |
| --- | --- |
| 2024 年 8 月 (渡豪直後) | 住居・通信・銀行・勤怠 |
| 2025 年 8 月 | 買い物 |
| 2026 年 2 月 | 買い物と配送 |
| 2026 年 8 月 (帰国後) | 求人・銀行・医療 |

`Housing` と `Work/Roster` は渡豪直後にしか出てこない。
**調査は複数の時期を跨いで行う。**

## 設計上の制約 (自分で課したもの)

### 1. 受信トレイから除外して既読にしてよいのは `Promotions` だけ

これを緩めると、Gmail フィルタで起きていた「静かに消える」が再発する。
`Security` / `Support` / `Official` / `Health` は**既読にもしない**。

### 2. `凍結日` はルール全体を止める

`凍結日` を過ぎたルールは新規メールに一切適用されない。ラベル付与も拠点付与も止まる。
新着にラベルを付けつつ過去にだけ拠点を付けたい場合は、**ルールを 2 行に分ける**。

### 3. 同じ送信元で取引と販促が分かれる場合、取引を先に評価する

Amazon が該当する。販促のルールが先に当たると、
`受信トレイ除外 + 既読` が効いて**注文確認が静かに消える**。

`Orders` 系の優先度を `Promotions` 系より小さくする。

これは運用の約束ではなく**コードで保証されている**。
`受信トレイ除外` または `既読化` が真のルールは、
**既に別の種別ラベルが付いたスレッドには適用されない** (`src/applier.ts`)。
拠点ラベル (`@` で始まるもの) とそのルール自身の付与先は判定から除くので、
1 通に `Promotions/Stores` と `@AU` の両方が付く並行付与は壊れない。

スキップされた分は `log` に `skipped: 既に分類済み` として残る。

### 4. ドライランと本適用でページ送りの扱いが違う

本適用では処理したスレッドにラベルが付き、`-label:"付与先"` の条件から外れるので
検索結果が減る。同じ `start` を読み直せばよい。
ドライランではラベルが付かないので結果が減らない。`start` を進めないと無限ループになる。

### 5. ラベルの削除は提案のみ

実削除は人間が Gmail 上で行う。誤削除の巻き戻しが効かないため。

### 6. ログにメール本文を書かない

件名は先頭 60 文字まで。送信元アドレスとラベル名以外の個人情報をシートに残さない。

### 7. ルールはシート側が正

コード内にドメインやアドレスをハードコードしない。
移行前の実態調査だけは例外としてコードに調査対象を持たせていたが、
移行の完了に伴い `src/sampler.ts` ごと削除した。現在は例外なし。
