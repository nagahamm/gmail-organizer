# 要件 — 振る舞いの定義

この仕組みが**何をするか**を Gherkin (Given / When / Then) で書いたもの。
実装がどうなっているかではなく、**利用者から見て何が起きるか**を書く。

機能に関わる変更は、着手前にここを更新する (`CLAUDE.md` の進め方)。
読んでいて「そんな動きは望んでいない」と思ったら、それは要件の誤りなので直す。

現時点では**すでに動いている振る舞い**を書き起こしてある。

---

## 前提となる用語

| 語 | 意味 |
| --- | --- |
| ルール | `rules` シートの 1 行。「この送信元はこのラベルへ」の対応 |
| 種別ラベル | `Finance` / `Promotions` など、メールの種別を表すラベル |
| 拠点ラベル | `@AU`。種別ラベルと**並行して**付く。`@` で始まる |
| ドライラン | `config` の `DRY_RUN` が `TRUE` の状態。ラベルを変えず記録だけ残す |

## 機能: 新着メールの自動振り分け

15 分ごとに動く。当初の課題「登録が面倒」に対して、一度ルールを登録すれば
以後は手を触れなくてよい状態にする。

```gherkin
シナリオ: ルールに一致した新着メールにラベルが付く
  前提 rules に「送信元ドメイン kuraveil.jp → Promotions/Jobs/Alerts」の有効なルールがある
  かつ DRY_RUN が FALSE である
  もし kuraveil.jp から新しいメールが届く
  ならば そのスレッドに Promotions/Jobs/Alerts が付く
  かつ log に付与の記録が残る

シナリオ: 優先度の小さいルールが先に評価される
  前提 同じ送信元に一致するルールが 2 つあり、優先度が 10 と 200 である
  もし その送信元からメールが届く
  ならば 優先度 10 のルールが先に適用される

シナリオ: 2 日より古いメールは新着の対象にならない
  前提 3 日前に届いた未分類のメールがある
  もし 15 分ごとの自動振り分けが動く
  ならば そのメールにはラベルが付かない
  # 取りこぼしは月次の遡及適用が拾う

シナリオ: どのルールにも一致しなければ何もしない
  前提 rules のどのルールにも一致しない送信元がある
  もし その送信元からメールが届く
  ならば ラベルは付かず、受信トレイにも残る
  かつ 週次ダイジェストの未分類一覧に挙がる
```

## 機能: 受信トレイから外すのは販促と、名指しした定型通知だけ

**この仕組みで最も守りたい線引き。** これを緩めると、Gmail フィルタで起きていた
「メールが静かに消える」が再発する。

```gherkin
シナリオ: 販促は受信トレイから外れて既読になる
  前提 「受信トレイ除外」と「既読化」を有効にした Promotions のルールがある
  もし そのルールに一致するメールが届く
  ならば そのスレッドは受信トレイから外れる
  かつ 既読になる

シナリオ: 販促以外は既定で受信トレイに残る
  前提 Finance / Security / Work などのルールがある
  もし そのルールに一致するメールが届く
  ならば ラベルは付く
  かつ 受信トレイに残る

シナリオ: 名指しした定型通知だけは販促でなくても外れる
  前提 送信元と件名で 1 行に特定した定型通知のルールがある
  かつ その行で「受信トレイ除外」を有効にしてある
  もし そのルールに一致するメールが届く
  ならば そのスレッドは受信トレイから外れる
  # ラベル単位では緩めない。同じラベルの他の行は残る

シナリオ: 安全側の大項目には例外を作らない
  前提 Security / Support / Official / Health のルールがある
  ならば 受信トレイから外さない
  かつ 既読にもしない

シナリオ: 取引メールが販促のルールで消されない
  前提 同じ送信元から注文確認と販促の両方が届く
  かつ その注文確認には既に Orders/Amazon が付いている
  もし 「受信トレイ除外」を持つ販促のルールが同じスレッドに一致する
  ならば そのスレッドは受信トレイから外れない
  かつ log に「既に分類済み」として記録される

シナリオ: 拠点ラベルは分類済みとみなさない
  前提 あるスレッドに @AU だけが付いている
  もし 「受信トレイ除外」を持つルールが一致する
  ならば そのルールは適用される
  # @AU と種別ラベルが両方付くのは正しい状態
```

## 機能: 既読化と受信トレイの保持

既読化は受信トレイ除外と**切り離す**。
「記録は残したいが毎回開く必要はない」ものを、受信トレイに残したまま既読にする。

```gherkin
シナリオ: 決済の都度通知は残したまま既読にする
  前提 カードや口座の利用通知にラベルを付けるルールがあり、既読化だけが有効である
  もし その通知が届く
  ならば ラベルが付く
  かつ 受信トレイに残る
  かつ 既読になる
  # 金額や利用先の記録は残るが、未読として注意を引かない

シナリオ: 不正利用の警告は既読にしない
  前提 身に覚えのない利用を知らせるメールが届く
  ならば Security/Alerts が付く
  かつ 未読のまま受信トレイに残る
  # 「利用しました」は流してよいが「身に覚えのない利用です」は流してはいけない

シナリオ: 保持期間を過ぎたら受信トレイから外す
  前提 ルールに受信トレイの保持期間が設定されている
  かつ そのラベルが付いたスレッドが受信トレイにあり、期間を過ぎている
  もし 定期実行が動く
  ならば そのスレッドは受信トレイから外れる
  かつ 削除はされない

シナリオ: 保持期間を設定していなければ外さない
  前提 ルールに受信トレイの保持期間が設定されていない
  かつ そのラベルを指す他のルールにも保持期間が無い
  もし どれだけ時間が経っても
  ならば そのスレッドは受信トレイに残り続ける
  # 保持期間はラベル単位で効く。設定するルールには専用のラベルを与える

シナリオ: 期間内のものは外さない
  前提 保持期間が 30 日のルールがある
  かつ そのラベルが付いたスレッドが 10 日前に届いている
  もし 定期実行が動く
  ならば そのスレッドは受信トレイに残る
```

## 機能: 凍結したルール

**終わった期間**のルールを、過去には効かせたまま新着には効かせない状態にする。
ルールを消すと過去メールを引けなくなるため。

`@AU` は一度この形で凍結したが、豪州からのメールが今も届くため解除した
(`docs/naming.md`)。機能そのものは残す。

```gherkin
シナリオ: 凍結したルールは新着に適用されない
  前提 凍結日が今日より前のルールがある
  もし そのルールに一致する新しいメールが届く
  ならば そのルールは適用されない

シナリオ: 凍結したルールも遡及には適用される
  前提 凍結日が今日より前のルールがある
  もし 過去メールへの遡及適用が動く
  ならば そのルールは適用される
```

## 機能: 過去メールへの遡及適用

Gmail フィルタでは絶対にできなかった「**後から効く**」を実現する部分。
毎月 1 日 0 時に動く。

⚠️ GAS の時間主導トリガーは**実行時刻を厳密に指定できない**。15 分間隔のものは
`installTriggers()` を実行した時刻が起点になり、以後そこから 15 分ごとに回る。
:00 / :15 / :30 / :45 に揃えたい場合は、毎時 :00 ちょうどに登録し直す。

```gherkin
シナリオ: 取りこぼしを月次で回収する
  前提 15 分ごとの自動振り分けが止まっていた期間がある
  もし 月次の遡及適用が動く
  ならば その期間に届いたメールにもルールが適用される

シナリオ: ルールを後から足しても過去に効く
  前提 新しいルールを rules に追加する
  もし 月次の遡及適用が動く
  ならば 対象期間内の過去メールにもそのルールが適用される

シナリオ: 6 分を超えたら続きから再開する
  前提 対象が多く 1 回の実行で終わらない
  もし 実行が時間切れで中断する
  ならば 次回の実行は中断した位置から再開する
  かつ 最初からやり直さない

シナリオ: ドライランの中断が本適用の再開位置を汚さない
  前提 DRY_RUN が TRUE で遡及適用を途中まで流した
  もし DRY_RUN を FALSE にして本適用する
  ならば 本適用は先頭から始まる

シナリオ: 1 ページに収まらないルールでも最後まで進む
  前提 1 つのルールの対象が 1 ページ (100 件) を超える
  もし 1 ページ目を処理してラベルが付き、検索結果が縮む
  ならば 縮んだぶんを飛び越さずに残りも処理する

シナリオ: 同じページを読み続けない
  前提 付けたラベルが検索インデックスにまだ反映されていない
  もし 同じ位置を読み直しても新しいスレッドが 1 件も無い
  ならば 次のページへ進む
```

### 過去メールの張り替え

行き先を変えたルールは、旧ラベルが「別の種別ラベル」として保護に引っかかり、
過去メールへ届かない。**印を付けた行だけ保護を外して流す**ための専用の入口を用意する。

```gherkin
シナリオ: 印を付けた行が過去メールに届く
  前提 行き先を変えたルールがあり、過去メールには旧ラベルが付いている
  かつ そのルールに「張り替え」の印を付けてある
  もし 張り替えを実行する
  ならば 旧ラベルが付いたままの過去メールにも新しいラベルが付く

シナリオ: 印の無い行は張り替えで動かない
  前提 「張り替え」の印が付いていないルールがある
  もし 張り替えを実行する
  ならば そのルールは評価されない

シナリオ: 張り替えでは受信トレイから外さず既読にもしない
  前提 「受信トレイ除外」と「既読化」を持つルールに印を付けてある
  もし 張り替えを実行する
  ならば ラベルは付くが、受信トレイからは外れず既読にもならない
  # 過去メールを整理するための実行であって、いま読むべきものを消す実行ではない

シナリオ: シートの設定は書き換わらない
  前提 「受信トレイ除外」が TRUE のルールに印を付けてある
  もし 張り替えを実行して終わる
  ならば その行の「受信トレイ除外」は TRUE のまま残る
  # 手で戻す手順を無くすため、そもそも書き換えない

シナリオ: 張り替えの中断が月次の再開位置を汚さない
  前提 張り替えが時間切れで中断した
  もし 月次の遡及適用が動く
  ならば 月次は自分の再開位置から始まる

シナリオ: 二度実行しても増えない
  前提 張り替えを最後まで実行した
  もし 印を付けたまま もう一度実行する
  ならば 既に新しいラベルが付いた過去メールは対象にならない

シナリオ: 旧ラベルは残る
  前提 張り替えで新しいラベルが付いた
  ならば 旧ラベルはそのまま残っている
  # ラベルの実削除は人間が Gmail 上で行う
```

### 何日かに分けて流す

全期間を対象にすると 1 日では終わらない。GAS の日次クォータを使い切る前に止め、
翌日に続きから流す。**利用者が毎日ボタンを押す必要は無い。**

```gherkin
シナリオ: 1 日の上限に達したら止める
  前提 対象が多く 1 日では終わらない
  もし その日に処理したスレッド数が上限に達する
  ならば そこで中断して再開位置を残す
  かつ その日はもう遡及を進めない

シナリオ: 翌日に続きから再開する
  前提 前日に上限で中断した遡及がある
  もし 日付が変わる
  ならば その日の使用量は 0 から数え直される
  かつ 中断した位置から自動で再開する

シナリオ: 再開は人が押さなくても進む
  前提 中断した遡及がある
  もし 15 分ごとの自動実行が動く
  ならば 続きが流れる

シナリオ: 中断していなければ何も起きない
  前提 再開位置が残っていない
  もし 15 分ごとの自動実行が動く
  ならば 遡及は始まらない
  # これを守らないと 15 分ごとに全期間の遡及が起動してクォータを使い切る

シナリオ: ドライランは自動では進まない
  前提 DRY_RUN が TRUE で遡及を途中まで流した
  もし 15 分ごとの自動実行が動く
  ならば 続きは流れない
  # ドライランは人が結果を見るための実行で、無人で進めるものではない

シナリオ: 張り替えと遡及で同じ 1 日分を使う
  前提 その日に張り替えでスレッドを処理した
  もし 同じ日に遡及適用が動く
  ならば 残りの予算だけを使う
  # 上限は Gmail アカウント単位で効くので、数え場所を分けると合計で超える
```

## 機能: 過去の未分類の洗い出し

遡及を流し切ったあとに残るのは、**ルールがそもそも無い送信元**である。
ルールは過去 1 年の観測から作ったので、それより前にしか出てこないものは拾えない。
受信トレイに限らず、アーカイブ済みも含めて棚卸しする。

```gherkin
シナリオ: アーカイブ済みでも未分類なら出てくる
  前提 ラベルの付いていない古いメールがアーカイブ済みで残っている
  もし 過去の未分類を洗い出す
  ならば その送信元が backlog に集計される

シナリオ: 自分が送ったメールは数えない
  前提 自分の送信済みメールにラベルが付いていない
  もし 過去の未分類を洗い出す
  ならば 送信済みと下書きは集計に入らない

シナリオ: ラベルが付いたものは残りに出てこない
  前提 遡及適用でラベルが付いたメールがある
  もし そのあとで過去の未分類を洗い出す
  ならば そのメールは backlog に出てこない
  # 先に遡及を流し切るほど、backlog は本当の残りだけになる

シナリオ: ルールを書くのに足る情報が出る
  前提 未分類の送信元が見つかった
  ならば 送信元・list_id・件数・最初と最後の受信日・代表件名が並ぶ
  # これだけあれば rules の 1 行が書ける

シナリオ: 週次の集計を壊さない
  前提 backlog に棚卸しの途中経過がある
  もし 日曜の週次ダイジェストが動く
  ならば backlog は消えない
  # unmatched は毎回置き換わる。寿命の違うものを同じシートに置かない

シナリオ: 洗い出しも何日かに分けて流れる
  前提 対象が多く 1 日では終わらない
  もし その日の上限に達する
  ならば 中断して再開位置を残し、翌日に続きから流れる

シナリオ: ラベルは決めてくれない
  前提 backlog に未分類の送信元が並んでいる
  ならば どのラベルへ入れるかは書かれていない
  # 出すのは「ルールが無い」という事実まで。行き先は人が決める
```

### 進み具合を見る

何日かに分けて流れる処理は、放っておくと「進んでいるのか止まっているのか」が
分からなくなる。**始めた人がその日に確かめられること**を優先する。

```gherkin
シナリオ: 中断中の処理があるか分かる
  前提 遡及適用が上限で中断している
  もし 実行の状態を見る
  ならば 中断中であることと、どこまで進んだかが分かる

シナリオ: 今日どれだけ使ったか分かる
  もし 実行の状態を見る
  ならば その日に処理したスレッド数と 1 日の上限が分かる

シナリオ: 何も動いていなければそう分かる
  前提 中断中の処理が無い
  もし 実行の状態を見る
  ならば 中断中の処理は無いと分かる

シナリオ: 見に行かなくても届く
  前提 中断中の処理がある
  もし 週次ダイジェストが動く
  ならば 同じ内容がダイジェストにも載る

シナリオ: 完了予定は出さない
  もし 実行の状態を見る
  ならば 残り時間や完了予定日は出てこない
  # 1 日に進む量は対象の密度で変わる。外れた予測は「止まっている」の誤認を生む
```

## 機能: スターによる求人の昇格

「関心が高い」は主観なので機械判定できない。かといって毎回ラベルを手で付けるのは
「登録が面倒」への逆戻りになる。**スターをワンタップの入力装置として使う。**

```gherkin
シナリオ: スターを付けた求人が昇格する
  前提 Promotions/Jobs 配下のラベルが付いたメールがある
  もし そのスレッドにスターを付ける
  ならば 15 分以内に Work/Shortlist が付く
  かつ 受信トレイに戻る
  かつ スターは外れる

シナリオ: 求人以外のスターには触れない
  前提 Promotions/Jobs 配下ではないスレッドにスターが付いている
  もし 昇格の処理が動く
  ならば そのスレッドは変更されない
  # 既存のスター 450 件以上を守るため
```

## 機能: 応募済みスレッドの検出

読み流す求人 (`Promotions/Jobs`) と、自分が動いている求人 (`Work`) を分ける。
**境界線は「自分がアクションしたかどうか」。**

```gherkin
シナリオ: 自分が返信したスレッドを提案する
  前提 求人のやり取りで自分から送信したメールを含むスレッドがある
  もし 応募済みスレッドの検出が動く
  ならば proposals に Work/Applications への提案が挙がる
  かつ 提案には「自分が返信したスレッド」という根拠が付く

シナリオ: 提案は自動では適用されない
  前提 proposals に未確認の提案がある
  もし 承認されないまま自動処理が動く
  ならば ラベルは変更されない
```

## 機能: 承認による学習

**この設計の要。** 「登録が面倒」への答えとして、利用者の操作を
**承認列のプルダウンを 1 つ変えるだけ**に圧縮する。

```gherkin
シナリオ: 承認するとルールになり過去にも効く
  前提 proposals に「この送信元を Promotions/Food へ」の提案がある
  もし 承認列を「承認」に変える
  ならば 次の自動実行で rules に行が追加される
  かつ そのルールが過去メールにも適用される
  かつ 提案の反映日が記入される

シナリオ: 提案されたラベルが無ければ作られる
  前提 提案が labels に無いラベルを指している
  もし その提案を承認する
  ならば そのラベルが labels に追加される

シナリオ: 却下した提案は繰り返し出てこない
  前提 proposals に提案がある
  もし 承認列を「却下」に変える
  ならば ルールは追加されない
  かつ 同じ送信元が再び提案されない
```

## 機能: 週次ダイジェスト

毎週日曜に届くメール。**何が起きているかを人が見る唯一の定期的な窓口。**

```gherkin
シナリオ: 未分類の送信元が届く
  前提 受信トレイにラベルの付いていないメールがある
  もし 週次ダイジェストが動く
  ならば 送信元ごとに集計された一覧がメールで届く
  かつ unmatched シートにも同じ内容が残る

シナリオ: 読んでいない送信元を受信トレイ除外の候補にする
  前提 ある送信元のメールが受信トレイにラベル無しで溜まっている
  かつ その送信元のメールをほとんど読んでいない
  ならば 「受信トレイ除外の候補」として印が付く

シナリオ: メインに入るものも候補にする
  前提 ある送信元のメールが Gmail のどのタブにも入らない
  かつ その送信元のメールをほとんど読んでいない
  ならば 受信トレイ除外の候補になる
  # メインにも販促がまとまった量で入り込んでいるため

シナリオ: 読んでいるものは候補にしない
  前提 ある送信元のメールを読んでいる
  もし 受信トレイに溜まっていても
  ならば 受信トレイ除外の候補にはしない
  # 個人のやり取りや取引メールはここで残る

シナリオ: 除外候補を提案に立てる
  前提 unmatched に「除外候補」の印が付いた送信元がある
  かつ その送信元をまだ提案していない
  もし 週次ダイジェストが動く
  ならば proposals に受信トレイ除外の提案が挙がる
  かつ 根拠にカテゴリ・件数・未読率が入る
  # ここは判断が要らない。Gmail の分類と未読率がそのまま答えになる

シナリオ: どのラベルへ入れるかは決めない
  前提 除外候補の提案を立てる
  ならば 提案ラベルは Promotions にする
  # ジャンルの判断は機械にはできない。承認する前に人がプルダウンで直す

シナリオ: 同じ送信元を繰り返し提案しない
  前提 ある送信元を既に提案している
  もし 週次ダイジェストがもう一度動く
  ならば その送信元は再び提案されない

シナリオ: 除外候補でないものは提案しない
  前提 unmatched に除外候補の印が付いていない送信元がある
  もし 週次ダイジェストが動く
  ならば その送信元は提案されない

シナリオ: 死んだルールが分かる
  前提 90 日間一度も一致していないルールがある
  もし 週次ダイジェストが動く
  ならば そのルールが一覧に挙がる
  # ルールの増殖に歯止めをかけるため
```

## 機能: シートの検査

シナリオ: 列の型に合わない値を報告する
  前提 数値の列に文字列が入っている

  前提 状態の列に決められた選択肢以外の値が入っている
  もし シートの検査が動く

  前提 rules のあるルールが labels に無いラベルを指している
  もし シートの検査が動く
  ならば そのルールが報告される
  # 有効化すると Gmail 側にそのラベルが作られてしまうため

  前提 シートに問題がある
  もし 週次ダイジェストが動く

## 機能: 取り込んだ Gmail フィルタの引き継ぎ

既存の Gmail フィルタは真実の源から降格させ、**凍結して並走**する。
一度に切り替えず、一致を確認できたものから順に引き継ぐ。

```gherkin
シナリオ: 取り込んだルールは確認するまで動かない
  もし 既存の Gmail フィルタを rules へ取り込む
  ならば 取り込んだ行はすべて無効の状態で入る
  かつ 人が確認するまで何も適用されない

シナリオ: 移行前のラベルを指す行に気づける
  前提 取り込んだ行が、ラベル体系の移行前の名前を指している
  もし シートの検査が動く
  ならば その行が報告される

シナリオ: 張り替えを済ませてから有効にする
  前提 取り込んだ行が移行前のラベル名を指している
  ならば 新しいラベル名へ張り替えるまで有効にしない
  # 有効にすると Gmail 側に旧ラベルが作り直され、移行が巻き戻る

シナリオ: 新体系に対応しない行は捨てる
  前提 取り込んだ行が Gmail のシステムラベルだけを指している
  ならば 新体系に対応するラベルが無いので、その行は削除する

シナリオ: 移行後のルールが既に拾っている送信元は張り替えない
  前提 取り込んだ行と同じ送信元を、移行後に手で書いたルールが既に拾っている
  ならば 張り替えずにその行を削除する
  # 両方が有効だと 1 通に種別ラベルが 2 つ付く

シナリオ: 有効化の前にドライランで確かめる
  前提 張り替えを終えた行がある
  もし DRY_RUN が TRUE のまま適用を実行する
  ならば ラベルは変わらず、log に何が起きるはずだったかが残る
  かつ それを見てから本適用に切り替える

シナリオ: 有効化は過去メールにも及ぶ
  前提 DRY_RUN が FALSE のまま取り込んだ行を有効にする
  もし 月次の遡及適用が動く
  ならば 過去 1 年分のメールにも受信トレイ除外と既読化が及ぶ
  # 有効化の前に DRY_RUN を TRUE へ戻す
```
