# 要件 — 振る舞いの定義

この仕組みが**何をするか**を Gherkin (Given / When / Then) で書いたもの。
実装がどうなっているかではなく、**利用者から見て何が起きるか**を書く。

機能に関わる変更は、着手前にここを更新する (`CLAUDE.md` の進め方)。
読んでいて「そんな動きは望んでいない」と思ったら、それは要件の誤りなので直す。

現時点では**すでに動いている振る舞い**を書き起こしてある。

---

## 前提となる用語

| 語 | 意味 |
| --- | --- |
| ルール | `rules` シートの 1 行。「この送信元はこのラベルへ」の対応 |
| 種別ラベル | `Finance` / `Promotions` など、メールの種別を表すラベル |
| 拠点ラベル | `@AU`。種別ラベルと**並行して**付く。`@` で始まる |
| ドライラン | `config` の `DRY_RUN` が `TRUE` の状態。ラベルを変えず記録だけ残す |

## 機能: 新着メールの自動振り分け

15 分ごとに動く。当初の課題「登録が面倒」に対して、一度ルールを登録すれば
以後は手を触れなくてよい状態にする。

```gherkin
シナリオ: ルールに一致した新着メールにラベルが付く
  前提 rules に「送信元ドメイン kuraveil.jp → Promotions/Jobs/Alerts」の有効なルールがある
  かつ DRY_RUN が FALSE である
  もし kuraveil.jp から新しいメールが届く
  ならば そのスレッドに Promotions/Jobs/Alerts が付く
  かつ log に付与の記録が残る

シナリオ: 優先度の小さいルールが先に評価される
  前提 同じ送信元に一致するルールが 2 つあり、優先度が 10 と 200 である
  もし その送信元からメールが届く
  ならば 優先度 10 のルールが先に適用される

シナリオ: 2 日より古いメールは新着の対象にならない
  前提 3 日前に届いた未分類のメールがある
  もし 15 分ごとの自動振り分けが動く
  ならば そのメールにはラベルが付かない
  # 取りこぼしは月次の遡及適用が拾う

シナリオ: どのルールにも一致しなければ何もしない
  前提 rules のどのルールにも一致しない送信元がある
  もし その送信元からメールが届く
  ならば ラベルは付かず、受信トレイにも残る
  かつ 週次ダイジェストの未分類一覧に挙がる
```

## 機能: 受信トレイから外してよいのは販促だけ

**この仕組みで最も守りたい線引き。** これを緩めると、Gmail フィルタで起きていた
「メールが静かに消える」が再発する。

```gherkin
シナリオ: 販促は受信トレイから外れて既読になる
  前提 「受信トレイ除外」と「既読化」を有効にした Promotions のルールがある
  もし そのルールに一致するメールが届く
  ならば そのスレッドは受信トレイから外れる
  かつ 既読になる

シナリオ: 販促以外は受信トレイに残り未読のままになる
  前提 Finance / Security / Work などのルールがある
  もし そのルールに一致するメールが届く
  ならば ラベルは付く
  かつ 受信トレイに残る
  かつ 未読のままになる

シナリオ: 取引メールが販促のルールで消されない
  前提 同じ送信元から注文確認と販促の両方が届く
  かつ その注文確認には既に Orders/Amazon が付いている
  もし 「受信トレイ除外」を持つ販促のルールが同じスレッドに一致する
  ならば そのスレッドは受信トレイから外れない
  かつ log に「既に分類済み」として記録される

シナリオ: 拠点ラベルは分類済みとみなさない
  前提 あるスレッドに @AU だけが付いている
  もし 「受信トレイ除外」を持つルールが一致する
  ならば そのルールは適用される
  # @AU と種別ラベルが両方付くのは正しい状態
```

## 機能: 凍結したルール

ワーホリのように**終わった期間**のルールを、過去には効かせたまま新着には
効かせない状態にする。ルールを消すと過去メールを引けなくなるため。

```gherkin
シナリオ: 凍結したルールは新着に適用されない
  前提 凍結日が今日より前のルールがある
  もし そのルールに一致する新しいメールが届く
  ならば そのルールは適用されない

シナリオ: 凍結したルールも遡及には適用される
  前提 凍結日が今日より前のルールがある
  もし 過去メールへの遡及適用が動く
  ならば そのルールは適用される
```

## 機能: 過去メールへの遡及適用

Gmail フィルタでは絶対にできなかった「**後から効く**」を実現する部分。
毎月 1 日に動く。

```gherkin
シナリオ: 取りこぼしを月次で回収する
  前提 15 分ごとの自動振り分けが止まっていた期間がある
  もし 月次の遡及適用が動く
  ならば その期間に届いたメールにもルールが適用される

シナリオ: ルールを後から足しても過去に効く
  前提 新しいルールを rules に追加する
  もし 月次の遡及適用が動く
  ならば 対象期間内の過去メールにもそのルールが適用される

シナリオ: 6 分を超えたら続きから再開する
  前提 対象が多く 1 回の実行で終わらない
  もし 実行が時間切れで中断する
  ならば 次回の実行は中断した位置から再開する
  かつ 最初からやり直さない

シナリオ: ドライランの中断が本適用の再開位置を汚さない
  前提 DRY_RUN が TRUE で遡及適用を途中まで流した
  もし DRY_RUN を FALSE にして本適用する
  ならば 本適用は先頭から始まる
```

## 機能: スターによる求人の昇格

「関心が高い」は主観なので機械判定できない。かといって毎回ラベルを手で付けるのは
「登録が面倒」への逆戻りになる。**スターをワンタップの入力装置として使う。**

```gherkin
シナリオ: スターを付けた求人が昇格する
  前提 Promotions/Jobs 配下のラベルが付いたメールがある
  もし そのスレッドにスターを付ける
  ならば 15 分以内に Work/Shortlist が付く
  かつ 受信トレイに戻る
  かつ スターは外れる

シナリオ: 求人以外のスターには触れない
  前提 Promotions/Jobs 配下ではないスレッドにスターが付いている
  もし 昇格の処理が動く
  ならば そのスレッドは変更されない
  # 既存のスター 450 件以上を守るため
```

## 機能: 応募済みスレッドの検出

読み流す求人 (`Promotions/Jobs`) と、自分が動いている求人 (`Work`) を分ける。
**境界線は「自分がアクションしたかどうか」。**

```gherkin
シナリオ: 自分が返信したスレッドを提案する
  前提 求人のやり取りで自分から送信したメールを含むスレッドがある
  もし 応募済みスレッドの検出が動く
  ならば proposals に Work/Applications への提案が挙がる
  かつ 提案には「自分が返信したスレッド」という根拠が付く

シナリオ: 提案は自動では適用されない
  前提 proposals に未確認の提案がある
  もし 承認されないまま自動処理が動く
  ならば ラベルは変更されない
```

## 機能: 承認による学習

**この設計の要。** 「登録が面倒」への答えとして、利用者の操作を
**承認列のプルダウンを 1 つ変えるだけ**に圧縮する。

```gherkin
シナリオ: 承認するとルールになり過去にも効く
  前提 proposals に「この送信元を Promotions/Food へ」の提案がある
  もし 承認列を「承認」に変える
  ならば 次の自動実行で rules に行が追加される
  かつ そのルールが過去メールにも適用される
  かつ 提案の反映日が記入される

シナリオ: 提案されたラベルが無ければ作られる
  前提 提案が labels に無いラベルを指している
  もし その提案を承認する
  ならば そのラベルが labels に追加される

シナリオ: 却下した提案は繰り返し出てこない
  前提 proposals に提案がある
  もし 承認列を「却下」に変える
  ならば ルールは追加されない
  かつ 同じ送信元が再び提案されない
```

## 機能: 週次ダイジェスト

毎週日曜に届くメール。**何が起きているかを人が見る唯一の定期的な窓口。**

```gherkin
シナリオ: 未分類の送信元が届く
  前提 受信トレイにラベルの付いていないメールがある
  もし 週次ダイジェストが動く
  ならば 送信元ごとに集計された一覧がメールで届く
  かつ unmatched シートにも同じ内容が残る

シナリオ: Gmail の分類を受信トレイ除外の根拠にする
  前提 ある送信元のメールが Gmail のプロモーション / ソーシャル / 新着に入っている
  かつ その送信元のメールをほとんど読んでいない
  ならば 「受信トレイ除外の候補」として印が付く

シナリオ: どのタブにも入らないものは除外候補にしない
  前提 ある送信元のメールが Gmail のどのカテゴリにも入らない
  もし 未読率が高くても
  ならば 受信トレイ除外の候補にはしない
  # 個人のやり取りや取引メールが多いため

シナリオ: 死んだルールが分かる
  前提 90 日間一度も一致していないルールがある
  もし 週次ダイジェストが動く
  ならば そのルールが一覧に挙がる
  # ルールの増殖に歯止めをかけるため
```

## 機能: シートの検査

シートは人が直接編集する。**壊れたことに気づけないのが一番困る。**

```gherkin
シナリオ: 列の型に合わない値を報告する
  前提 数値の列に文字列が入っている
  もし シートの検査が動く
  ならば そのセルの位置と内容が報告される

シナリオ: 選択肢にない値を報告する
  前提 状態の列に決められた選択肢以外の値が入っている
  もし シートの検査が動く
  ならば そのセルが報告される

シナリオ: 存在しないラベルを指すルールを報告する
  前提 rules のあるルールが labels に無いラベルを指している
  もし シートの検査が動く
  ならば そのルールが報告される
  # 有効化すると Gmail 側にそのラベルが作られてしまうため

シナリオ: 検査結果は週次でも目に入る
  前提 シートに問題がある
  もし 週次ダイジェストが動く
  ならば ダイジェストのメールに問題が含まれる
  # 人が検査を実行し忘れても気づけるようにする

シナリオ: ヘッダが壊れていたら止まる
  前提 シートの列名が書き換わっている
  もし シートの作成 / 更新が動く
  ならば 列を追加せずエラーで止まる
  # 黙って別の列へ書き込みが流れるのを防ぐ
```

## 機能: ドライラン

**破壊的な操作の前に必ず通す安全弁。**

```gherkin
シナリオ: ドライランではラベルが変わらない
  前提 DRY_RUN が TRUE である
  もし 振り分けや遡及適用が動く
  ならば ラベルは一切変更されない
  かつ log に「何をするつもりだったか」が dry_run として記録される

シナリオ: 初期状態は安全側になっている
  前提 setup を実行した直後である
  もし 何も設定を変えない
  ならば DRY_RUN は TRUE である
```

## 機能: ラベルの階層

```gherkin
シナリオ: ラベルを作ると親も作られる
  前提 Learning という親ラベルが存在しない
  もし Learning/Exams が作られる
  ならば Learning も同時に作られる
  # 親が実在しないと Gmail のサイドバーで入れ子にならない

シナリオ: すでに平坦になっているラベルを後から救える
  前提 親のないラベルが既に存在する
  もし 「親ラベルを作る」を実行する
  ならば 不足している親がすべて作られる
```

## 機能: 守ること

利用者の資産を壊さないための決めごと。

```gherkin
シナリオ: メール本文は記録されない
  もし どの処理が動いても
  ならば log にメール本文は書かれない
  かつ 件名は先頭 60 文字までしか残らない

シナリオ: ラベルは自動削除されない
  前提 使われていないラベルがある
  もし 週次ダイジェストが動く
  ならば 削除は提案されるだけで実行されない
  # 誤削除の巻き戻しが効かないため

シナリオ: 振り分けの正はシートにある
  前提 rules シートを書き換える
  もし 次の自動実行が動く
  ならば 書き換えた内容が反映される
  # コードにドメインやアドレスを書かない
```

## まだ要件になっていないもの

以下は動いているが、要件として固まっていない。触るときにここへ書き起こす。

- 送信元マスタ (`senders`) の使いみち。プログラムからは誰も読んでいない
- 週次 AI (Claude の Routine) が `unmatched` を読んで `proposals` を書く部分。
  **設定されているか未確認**
- 取り込んだ旧 Gmail フィルタ 89 行の扱い
