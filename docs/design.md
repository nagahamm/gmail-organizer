# 設計メモ — Gmail ラベル自動振り分け

作成日: 2026-08-19 / 対象アカウント: hurwa8@gmail.com

---

## 1. 現状の棚卸し

Gmail API で実データを取得した結果 (2026-08-19 時点)。

| 指標 | 値 |
| --- | --- |
| 受信トレイ | **11,642 通** (未読 9,225 通) |
| 全体の未読 | 10,489 通 |
| ユーザー定義ラベル | 39 個 |
| 大項目 (トップレベル) | 5 個 — `Australia` / `ファイナンス` / `プロモーション` / `Schedules` / `Authentication` |
| 3 階層まで使っているラベル | **1 個だけ** (`Australia/AWX/Payslip`) |

受信トレイに 11,642 通が残っているのが、フィルタが機能していないことの直接的な証拠です。

### 1.1 見つかった問題

**① 軸が混ざっている (最大の構造問題)**

大項目の 5 つが、それぞれ**別の分類軸**になっています。

| 大項目 | 実際の軸 |
| --- | --- |
| `プロモーション` | メールの**種別** (販促かどうか) |
| `Australia` | **拠点 / 生活圏** |
| `ファイナンス` | **ドメイン** (お金) |
| `Schedules` / `Authentication` | メールの**種別** |

軸が違うものを同じ階層に並べたので、同じ概念が両方に現れています。

- `プロモーション/Stores` (480) ↔ `Australia/Stores` (2,039)
- `プロモーション/Meal` (1,497) ↔ `Australia/Meal` (0)
- `プロモーション/Employment` (5,418) ↔ `Australia/Employment` (1,223)

「オーストラリアの店からの販促メール」がどちらに入るべきか決まらない。これが
**振り分けルールを書くたびに迷い、ルールが増殖した根本原因**です。

**② `from:` のワイルドカードが効いていない**

スクリーンショットのフィルタに以下の記述があります。

```
from:({ from: *.agoda-emails.com  from: *@jalan\.net  ... })
```

Gmail のフィルタは **glob (`*`) をサポートしていません**。`*` はワイルドカードとして
解釈されず、部分一致的に処理されるため、意図しないマッチ / ノーマッチが起きます。
これが「うまく動かない時がある」の有力な原因です。

**③ フィルタの上限に近づく書き方をしている**

Gmail は 1 アカウント **1,000 フィルタ**、1 フィルタあたり**クエリ 1,500 文字**が上限です。
現在の「1 つのフィルタに `from:` を `{ }` で大量に束ねる」書き方は、フィルタ数の上限を
避けるための苦肉の策ですが、束が育つと 1,500 文字上限にぶつかって静かに壊れます。

**④ 遡及しない・ログが残らない・失敗に気づけない**

- フィルタは**受信時にしか走らない**。ルールを直しても過去メールは直らない。
- 何がなぜ振り分けられたかの**記録がない**。デバッグができない。
- 「受信トレイをスキップ + 既読にする」が効くとメールが**静かに消える**ので、
  誤爆しても気づけない。

**⑤ 死んだラベルと命名ゆれ**

- 件数 0 のラベル: `Australia/Accommodations`, `Australia/Meal`, および親のみのプレースホルダ 5 個
- `Authentication/Login` は **1 通**しかない (認証メールが分類できていない)
- `プロモーション/Creater` は `Creator` の綴り間違い
- `Cashback rewards` だけ空白入り・小文字始まり
- 日英混在: `楽天カード` / `楽天証券` vs `CreditCards` / `DebitCards`

## 2. 決定した方針

| 論点 | 決定 |
| --- | --- |
| ラベルの軸 | **A: 種別を大項目・拠点は並行ラベル** |
| 既存 11,642 通 | **直近 1 年に遡及適用** (ドライラン先行) |
| 週次 AI | **Claude の週次 Routine** |
| 既存 Gmail フィルタ | **凍結して並走 → 段階移行** |

### 2.1 なぜ「拠点を並行ラベル」なのか

**Gmail はフォルダではなくタグ**です。1 通に複数ラベルを付けられます。
無理に 1 本の木に押し込むから破綻するので、軸を 2 本に分けます。

```
軸1: 種別 (階層 3 段)          軸2: 拠点 (フラット)
  Finance/Cards/Rakuten         @AU   ← 凍結済み
  Promotions/Stores
  Work/AWX/Payslips
```

「オーストラリアの店からの販促メール」は `Promotions/Stores` **と** `@AU` の
両方が付きます。どちらに入れるか迷う問題が構造的に消えます。

**ワーホリは終了済み**なので、`@AU` はアクティブな分類軸ではなく
最初から「過去を掘り出すためのマーカー」です。移行時に既存メールへ遡及付与するだけで、
新規メールには付けません。AU 関連ルールは `凍結日` を移行日に設定して取り込みます。
ラベル自体は過去メールの検索性のために残します。

`凍結日` と `有効 = FALSE` は別物です。`有効 = FALSE` はルールを完全に止めますが、
`凍結日` は**過去メールへの遡及適用は許し、新規メールにだけ適用しない**。
既存の 4,944 通に `@AU` を付けたうえで、今後は増やさない、という挙動がこれで作れます。

**`@JP` は作りません。** `@AU` でないものは全部 JP なので、9,000 通以上に
無意味なタグが付くだけです。3 つ目の拠点が出てきたら、そのとき追加します。

### 2.2 新しいラベル体系

**ラベル名は英語**。大項目・中項目は英語、小項目のブランド名のみ原語
(`Rakuten` / `Amazon` / `AWX`)。

| 大項目 | 意味 | 受信トレイ | 既読化 |
| --- | --- | --- | --- |
| `Finance` | 口座・カード・証券・決済・請求 | 残す | しない |
| `Orders` | EC 注文・発送・領収 | 残す | しない |
| `Subscriptions` | 定期課金しているサービス | 残す | しない |
| `Utilities` | 通信・電気・ガス・水道・有料道路 | 残す | しない |
| `Promotions` | ニュースレター・広告 | **除外** | **する** |
| `Security` | OTP・ログイン通知・不正利用の警告 | 残す | しない |
| `Schedule` | 予約・イベント | 残す | しない |
| `Work` | 就職活動・勤務先 | 残す | しない |
| `Learning` | 学習・資格試験 | 残す | しない |
| `Health` | 医療 | 残す | しない |
| `Housing` | 住居・シェアハウス・賃貸 | 残す | しない |
| `Support` | 問い合わせ中の案件 | 残す | しない |
| `Official` | 行政・税務・ビザ | 残す | しない |
| `Personal` | 人から届いたメール | 残す | しない |

**除外して既読にしてよいのは `Promotions` だけ**という線引きにする。
これを緩めると、Gmail フィルタで起きていた「静かに消える」が再発する。

命名は `docs/naming.md` に従う。可算名詞は複数形、不可算名詞は単数形。

拠点ラベル: `@AU` (先頭 `@` でラベル一覧の上部に固まり、視覚的にも区別できる)

### 2.3 求人を `Promotions/Jobs` と `Work` に二分する

求人系は 6,641 通あり、全ラベル中で最大の塊です。ここを
「応募したやつ / リクルート系 / 関心が高いやつ / バイト」で並列に分けると、
**また軸が混ざります** (自分の行動 / 送信元 / 主観評価 / 雇用形態)。

一番効く境界線は**「自分がアクションしたかどうか」**です。応募済みは埋もれたら困る、
求人アラートは読み流すもの。扱いが正反対なので大項目のレベルで割ります。

```
Promotions/Jobs/Agencies  リクルート系      ┐ 受信トレイ除外 + 既読
Promotions/Jobs/Temp      派遣・バイト      │ (読み流す側)
Promotions/Jobs/Alerts    一般の求人アラート ┘

Work/Applications         応募済み          ┐ 受信トレイに残す
Work/Shortlist            関心が高い         │ (自分が動いている側)
Work/AWX                  勤務先            ┘
```

**`Work/Applications` は自動判定できます。** 最強のシグナルは
「スレッドに自分の送信メールが含まれているか」。`GmailThread.getMessages()` を回して
`from` が自分なら、そのスレッドは自分がアクションを起こしたものだと判定できます。
求人アラートは一方通行なので、この 1 点でほぼ切り分けられます。
補助として件名パターン (`ご応募` / `選考` / `Application received` / `Thanks for applying`) も併用。

**`Work/Shortlist` はスターを入力装置にします。** 「関心が高い」は主観なので機械判定できません。
毎回ラベルを手で付けるのも面倒です。そこで:

```
Promotions/Jobs/* のメールにスターを付ける
        ↓ 次の GAS 実行 (15分以内)
Work/Shortlist に昇格 + 受信トレイに戻す + スターは外す
        ↓ 週次
Claude が Watching の傾向を学習し、似た求人を次から拾うルールを提案
```

スマホでもワンタップで済み、状態はラベルとして残り、続けるほど手作業が減ります。
承認ループと同じ思想です。

移行マッピングの全 39 ラベル分は `docs/label-migration.md` にあります。

## 3. アーキテクチャ

```
┌─────────────────────────────────────────────────────────┐
│  Google スプレッドシート  "Gmail Label DB"   ← 真実の源   │
│  labels / rules / log / unmatched / proposals            │
└───────────┬─────────────────────────────▲───────────────┘
            │ 読む                          │ 書く
            ▼                              │
┌─────────────────────────────┐            │
│  Google Apps Script          │            │
│  ・15分ごと: 新着に適用       │            │
│  ・週次:    集計 → unmatched │────────────┘
│  ・手動:    遡及バッチ        │
└───────────┬─────────────────┘
            │ GmailApp
            ▼
      ┌───────────┐        ┌──────────────────────────┐
      │  Gmail    │        │  Claude 週次 Routine      │
      └───────────┘        │  unmatched を読む         │
                           │  → proposals に提案を書く  │
                           └──────────────────────────┘
                                        │
                                   人間が承認列を
                                   プルダウンで変更
                                        │
                                        ▼
                             次回 GAS 実行が rules に反映
```

**承認ループがこの設計の要**です。「登録が面倒」という課題に対して、
ユーザーの操作を**プルダウンを 1 つ変えるだけ**に圧縮します。

## 4. スプレッドシートのスキーマ

### 4.1 `labels` — ラベルマスタ

| 列 | 内容 |
| --- | --- |
| `label_key` | 一意キー (自動採番) |
| `大項目` / `中項目` / `小項目` | 3 階層。小項目は空可 |
| `full_path` | `=TEXTJOIN("/",TRUE,...)` の数式。Gmail 上のラベル名そのもの |
| `gmail_label_id` | 同期時に GAS が自動記入 |
| `既定_受信トレイ除外` | チェックボックス |
| `既定_既読化` | チェックボックス |
| `状態` | `active` / `archived` |
| `説明` | 用途メモ |
| `件数` | 週次で GAS が自動更新 |

### 4.2 `rules` — メーリングリスト ↔ ラベル (中核)

| 列 | 内容 |
| --- | --- |
| `rule_id` | 自動採番 |
| `有効` | チェックボックス |
| `優先度` | 数値。小さいほど先に評価 |
| `種別` | `list_id` / `from` / `from_domain` / `subject` / `query` |
| `パターン` | 例: `newsletter.trip.com` |
| `ラベル` | `labels.full_path` からのプルダウン (入力規則で縛る) |
| `拠点` | `@AU` / `@JP` / 空 |
| `受信トレイ除外` / `既読化` / `スター` / `迷惑メールにしない` | ラベル既定値の上書き |
| `凍結日` | この日以降は新規メールに適用しない (`@AU` の段階的な終了に使う) |
| `メモ` | 自由記述 |
| `登録日` / `最終マッチ日` / `累計マッチ数` | GAS が自動更新 |

**`種別 = list_id` を第一級に扱うのが技術的な肝**です。メーリングリストは
`List-Id` / `List-Unsubscribe` ヘッダを持つので、Gmail 検索の `list:` 演算子で
確実に引けます。`from:` のワイルドカードより桁違いに安定します。
ご要望の「メーリングリストと項目を引っ付けておく」への直接の答えがこれです。

`最終マッチ日` があると「半年マッチしていない = 死んだルール」が一目で分かり、
ルールの増殖に歯止めがかかります。

### 4.3 `log` — 実行ログ

| 列 | 内容 |
| --- | --- |
| `run_id` / `実行時刻` | |
| `message_id` | 追跡用 |
| `from` / `list_id` | |
| `subject` | **先頭 60 文字まで**。本文は記録しない |
| `matched_rule_id` | 未マッチなら空 |
| `付与ラベル` / `アクション` | |
| `結果` | `applied` / `dry_run` / `error:...` |

行数が増えるので、6 か月より古い行は週次で別シートへ退避します。

### 4.4 `unmatched` — 未分類の集計 (AI の入力)

| 列 | 内容 |
| --- | --- |
| `送信元` / `list_id` | |
| `直近7日件数` / `累計件数` | |
| `未読率` | **開封していない = 読む気がない**の指標 |
| `初回受信日` | |
| `提案済み` | 同じ提案を繰り返さないためのフラグ |

### 4.5 `proposals` — AI 提案と承認

| 列 | 内容 |
| --- | --- |
| `提案日` / `提案ID` | |
| `種別` | `new_rule` / `new_label` / `inbox_skip` / `rename_label` / `archive_label` / `unsubscribe` |
| `根拠` | 例: 「直近 7 日で 34 通、未読率 100%」 |
| `提案内容` | 例: `list:news.example.com → 販促/ストア` |
| `承認` | **プルダウン**: 未確認 / 承認 / 却下 / 保留 |
| `反映日` | GAS が記入 |

想定される提案の形は、ご要望の 3 つがそのまま乗ります。

- 「定期購読しているメールを○○のラベルに振り分けませんか？」 → `new_rule`
- 「項目を新たに作って、このメーリングリストを振り分けますか？」 → `new_label` + `new_rule`
- 「○○からの受信が増えていますが、受信トレイから外しますか？」 → `inbox_skip`

## 5. サービス選定

| レイヤ | 採用 | 理由 |
| --- | --- | --- |
| DB | Google スプレッドシート | ご指定通り。GAS からネイティブに読める |
| 実行基盤 | **Google Apps Script** | 後述 |
| ソース管理 | このリポジトリ + clasp + TypeScript | GAS の Web エディタは保守が辛い |
| 週次 AI | Claude の Routine | 決定済み |
| 通知 | 自分宛メール + シート | |

### 5.1 なぜ GAS か (対抗案との比較)

**対抗案: Python + GitHub Actions (cron) + Gmail API**

一見きれいですが、個人 Gmail では**OAuth の罠**があります。Google Cloud プロジェクトを作り
同意画面を設定する必要があり、公開ステータスが「テスト」のままだと
**リフレッシュトークンが 7 日で失効**します。毎週手で認証し直すことになり、
「週次で自動実行」という目的と正面から衝突します。回避するには本番公開への
切り替えが要り、個人利用にしては手間が大きい。

**GAS を採用する理由:**

- OAuth クライアント / サービスアカウント / シークレット管理が**一切不要**
- `GmailApp` と `SpreadsheetApp` が**同一認証**で使える
- 時間主導トリガーが**PC の電源に依存せず**動く
- 無料

### 5.2 GAS の制約と対処

| 制約 | 対処 |
| --- | --- |
| 実行 6 分 / 回 | 遡及適用は `PropertiesService` にカーソルを保存する「続きから」方式で分割実行 |
| `GmailApp` 日次クォータ (読み取り系 20,000 操作 / 日 程度) | 遡及バッチはクォータ残を監視し、閾値で自走停止 |
| `GmailApp.search()` の 1 回あたり件数 | 500 件を目安に `start` / `max` でページング |

### 5.3 Claude Routine の未検証点 (正直に記載)

週次 Routine のセッションから **Gmail / Drive の MCP が使えるかは実装時に検証が必要**です。
使えなかった場合のフォールバックを用意します。

- GAS が週次ダイジェストを**シートに書き、同時に自分宛メールでも送る**
- Routine はシート (Drive MCP) かメール (Gmail MCP) のどちらか使える方を読む
- どちらも不可なら、GAS + Gemini API に切り替え (この場合も `proposals` シートの
  スキーマは変わらないので、書き手だけ差し替えれば済む設計にしておく)

## 6. 導入ステップ

| # | 内容 | 備考 |
| --- | --- | --- |
| 1 | スプレッドシート `Gmail Label DB` を作成 | 空でよい |
| 2 | コンテナバインド型の GAS プロジェクトを作成 | シートの拡張機能メニューから |
| 3 | clasp セットアップ、`src/` を push | このリポジトリ |
| 4 | `setup()` 実行 — 5 シート生成 + 入力規則 + 条件付き書式 | |
| 5 | **`importCurrentState()` 実行** — 既存 39 ラベルと Gmail フィルタをシートへ取り込む | **初期登録コストがここでゼロになる** |
| 6 | `docs/label-migration.md` に沿ってラベル体系を移行 | 人間のレビューが要る |
| 7 | `DRY_RUN = true` で実行 → `log` を確認 | **誤爆の確認はここだけ** |
| 8 | 本適用 (新着のみ) を 15 分トリガーで開始 | |
| 9 | 遡及バッチ (直近 1 年) を分割実行 | |
| 10 | 週次 Claude Routine を設定 | |
| 11 | ログで一致を確認できた既存 Gmail フィルタから順に削除 | 段階移行 |

ステップ 5 が効きます。「登録が面倒」という課題に対し、**今ある 39 ラベルと
既存フィルタの `from:` を機械的に吸い出して初期データにする**ので、
手入力はほぼ発生しません。

## 7. 未決事項

いずれも**推測で決めず、GAS でサンプリングしてから確定**するのが安全です。

1. **`Australia/Stores` (2,039 通) に取引メールが混ざっていないか** — 注文確認・
   発送通知が混ざっていれば `Orders/*` と `Promotions/Stores` に分割が要ります。
2. **求人 6,641 通の送信元内訳** — `Promotions/Jobs` を `Agencies` / `Temp` / `Alerts` に
   割る閾値は、実際の送信元ドメイン分布を見ないと決まりません。上位 20 ドメインで
   9 割はカバーできるはずです。
3. **`Work/Applications` の遡及判定がどこまで効くか** — 送信済みメールが 84 通しかないため、
   応募がプラットフォーム内で完結している (Indeed 経由など) 場合は
   スレッドに自分の送信が現れません。その場合は件名パターン頼みになります。
4. **`Promotions` を受信トレイ除外の既定にしてよいか** — 現在の運用と同じですが、
   見落としが怖ければ「除外はするが既読にはしない」に緩められます。
5. **未読 9,225 通を既読にするか** — `Promotions` 配下は既読化してよさそうですが、
   `Finance` / `Security` / `Work` は未読のまま残す方が安全です。
